LLM-GS · Lesson 0001 · 約 5 分鐘

為什麼 matrix run 會變慢？

把它想成「48 個實驗 arm 排隊，每個 arm 又可能找多個候選、修理失敗候選，而每次找候選還可能重問模型」。

先記住一句話

慢，不是因為一個迴圈失控；是因為多個有限的迴圈相乘。
矩陣數量 × 候選數量 × 修復輪次 × 單次回覆校正次數。

圖一：整個 matrix run

flowchart TD A[讀取 matrix YAML] --> B[建立 arms] B --> C[1 replicate × 4 tasks × 3 search × 4 failure = 48 arms] C --> D{逐一執行 arm} D --> E[建立 memory-training candidate] E --> F[產生 development candidates] F --> G{候選失敗？} G -- 否 --> H[選出 candidate] G -- 是 --> I[regenerate 或 repair] I --> J{最多 max_repair_cycles=1} J -- 再試 --> F J -- 結束 --> H H --> K[held-out evaluation：本地 evaluator] K --> D D --> L[輸出 matrix report]

注意：held-out evaluation 本身不是 LLM 呼叫；真正昂貴的是 E、F、I。

圖二：一個候選就可能再放大

flowchart LR A[要求模型產生程式] --> B{JSON / DSL 合法？} B -- 是 --> C[候選完成：1 request] B -- 否 --> D[建立 correction prompt] D --> E[再問模型] E --> F{仍不合法？} F -- 否 --> C F -- 是 --> G[最後一次 correction] G --> H[最多總共 3 requests] C --> I{development 失敗？} I -- 是 --> J[repair / regenerate] J --> A

所以「一個候選」不是固定 1 次模型回覆，而是最多 3 次；如果評估失敗，還會再開一個候選流程。

用目前設定算數字

目前 YAML 是 1 個 replicate、每個 arm 有 1 個 memory-training seed、1 個 development seed、1 個 held-out seed，且 max_repair_cycles: 1。

single_candidate：population 1 候選／修復上限 = 1 × (1 + 1) = 2 模型 request 上限 = 2 × 3 = 6 / arm cem、cebs：population 4 候選／修復上限 = 4 × (1 + 1) = 8 模型 request 上限 = 8 × 3 = 24 / arm 總上限 = 16 × 6 + 32 × 24 = 864 requests

這是上限，不是每次必然達到；但它解釋了為何一次完整矩陣會很慢。

練習：找出哪一層在放大

假設只跑一個 cem + reflect arm，population=4，且每個候選第一次都輸出非法 DSL，第二次才成功。

  1. 每個候選需要幾次模型 request？
  2. 四個候選一共幾次？
  3. 若其中一個候選評估失敗，再做一次 repair，且 repair 也需要兩次回覆，總數是多少？
查看答案

1. 每個候選 2 次。2. 4×2=8 次。3. 8+2=10 次。這還沒算其他 arm。

回到程式碼時看哪裡

  • matrix.py:20：arm 的笛卡兒積。
  • cli.py:229：arm 順序執行。
  • execution.py:357：population candidates。
  • execution.py:420：失敗後 repair／regenerate。
  • proposer.py:228：單次候選最多 3 次 request。
